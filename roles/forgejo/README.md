# forgejo

Forgejo (GPL-3.0-or-later) for source control, pull requests with required reviews (CHG-01) and
Forgejo Actions (CHG-02, with `roles/forgejo_runner`). Deployed by `playbooks/delivery.yml` on the
`forgejo` group. The image is the upstream rootless image `codeberg.org/forgejo/forgejo` pinned in
`roles/versions` (Forgejo 15, the LTS branch).

## What "highly available" means here

Forgejo has no built-in replication. Every node must see the same Git repositories, and upstream does
not document or test several Forgejo processes writing the same data. The role therefore offers:

| Mode | Serving nodes | Requirements | Failover |
| --- | --- | --- | --- |
| `active_passive` (default) | one | `forgejo_vips`; `forgejo_data_dir` on a volume the storage layer replicates or shares (DRBD, ZFS send/receive, SAN or cloud volume, NFS) | keepalived moves the VIP; the node that gets it runs `forgejo_failover_promote_command` and starts Forgejo; the node that loses it stops Forgejo and runs `forgejo_failover_demote_command`. Typical RTO: a minute plus the time to attach the volume. |
| `active_active` | all | repositories (`forgejo_repo_dir`) on shared POSIX storage (NFS/CephFS, checked with `findmnt`), S3 (`forgejo_s3_*`), Valkey/Redis (`forgejo_cache_*`) | the edge health check (`/api/healthz`) takes a failed node out. Upstream-untested: Forgejo's cron jobs run on every node, and Git on network filesystems depends on correct locking. Test on your storage first. |
| `standalone` | one | `forgejo_allow_single_node: true` | none (labs and tests) |

PostgreSQL (`forgejo_db_*`), object storage (`forgejo_s3_*`) and the cache (`forgejo_cache_*`) come
from the data layer and carry their own HA. With `forgejo_s3_endpoint` set, LFS objects,
attachments, avatars, packages and Actions logs and artifacts live in the bucket; without it they
stay under `forgejo_data_dir` (active/passive and labs only).

In active/passive mode the role does not replicate the volume itself and does not fence: a network
partition between the nodes can make both hold the VIP. Use storage that refuses a second writer
(DRBD with fencing/quorum, a cloud volume that attaches to one VM) and watch the `ForgejoSplitBrain`
alert (`forgejo_failover_active` summed over the nodes). The failover service
(`forgejo-failover.service`) also gives up the VIP when the active Forgejo fails its health check
for `forgejo_failover_unhealthy_checks` checks in a row, and writes `forgejo_failover_*` metrics to
the node_exporter textfile collector. A recovered preferred node takes the VIP back after
`forgejo_failover_preempt_delay` seconds (another short outage); raise it, or swap the order of the
hosts, to avoid the move.

## Identity (IAM-01, IAM-09)

- Keycloak client registered with `oidc_client`; the login source (`forgejo_oidc_name`) is created with
  `forgejo admin auth add-oauth` and updated when its settings change. The `roles` claim is the group
  claim: `platform-admin` becomes a Forgejo site admin (and loses it when the role goes); everyone
  else is a normal user. Optional `forgejo_oidc_restricted_role` makes a role "restricted".
- Users register only through OIDC (`ALLOW_ONLY_EXTERNAL_REGISTRATION`), are never linked to existing
  local accounts by e-mail, and are not asked for a Forgejo-local second factor (Keycloak enforces MFA).
- Password sign-in is off for everyone: no login form (`ENABLE_INTERNAL_SIGNIN = false`) and no HTTP
  basic auth with passwords (tokens still work for Git and the API).
- Break-glass: the local site admin `forgejo_admin_user` (password in the vault). Set
  `forgejo_break_glass_login: true` and run the playbook to bring the form back during an incident;
  site admins need a second factor (`GLOBAL_TWO_FACTOR_REQUIREMENT = admin`), so enrol TOTP for the
  break-glass account on first use and seal the recovery codes with the password. Root on a Forgejo
  host can also use `docker exec forgejo forgejo admin ...` (logged by auditd).
- `forgejo_automation_user` is a local machine account with no usable password; it owns the managed
  organisations and calls the API with a token generated by the CLI (kept root-only in
  `/opt/forgejo/secrets`, or supplied as `forgejo_automation_token`).
- Organisation and team membership is not derived from the `groups` claim by default. Either add
  people to teams in the UI or API (`PUT /api/v1/teams/{id}/members/{username}`), or set
  `forgejo_oidc_group_team_map`, e.g. `{"developer": {"platform": ["developers"]}, "operator":
  {"platform": ["operators"]}}` (roles claim values to organisation teams, applied at each login and
  removed when the role goes). Create the teams first.

## Change approval (CHG-01)

`tasks_from: org_setup` (second play of `playbooks/delivery.yml`) creates `forgejo_orgs`, their
repositories (private, default branch `main`) and branch protection from
`forgejo_branch_protection_template`: no direct or force pushes, 1 required approval, stale approvals
dismissed, rejected reviews, outdated branches and failing or missing status checks block the merge,
and the rules apply to admins. Forgejo forbids approving one's own pull request. The play checks each
rule against that policy, corrects drift, and exports the rules to
`forgejo_evidence_dir/branch-protection-<org>_<repo>.json` on the controller (CI keeps it as a run
artifact). Signed commits are verified (GPG and SSH keys, trust model `collaboratorcommitter`);
set `require_signed_commits: true` in the template or per repository to require them.

## Incident tracker (INC-01)

With `forgejo_incident_tracker_enabled`, org_setup also creates `forgejo_incident_tracker_org`/
`forgejo_incident_tracker_repo` (protected like the other repositories), the labels in
`forgejo_incident_labels` (incident, sev1..sev4, postmortem-needed, postmortem, security) and the issue
templates from `docs/templates` in `.forgejo/ISSUE_TEMPLATE/`. The templates go straight to `main` on the
first run, before it is protected; later changes are proposed as a pull request from
`forgejo_incident_template_branch`. The settings are exported to `forgejo_evidence_dir/incident-tracker.json`.
Every node also gets `forgejo-incident-export.timer`: monthly, the active node exports all incident issues
with their comments to `forgejo_incident_export_dir` (append-only backup) and writes retention metrics for
the alerts in `group_vars/monitoring/incidents.yml` (docs/incident-response.md).

## Backup and recovery (BCK-01, BCK-04)

`/usr/local/sbin/forgejo-backup-dump` (the backup `pre_command`) runs `forgejo dump` on the active
node into `forgejo_dump_dir/forgejo-dump.tar.gz`: the database as SQL, the repositories, the
configuration (with its secrets; the backup is encrypted) and local data. Object storage is left out
when S3 is used; protect the bucket with versioning or replication. A standby keeps its last dump.
RPO 24 h and RTO 4 h by default (`forgejo_backup_rpo_hours`, `forgejo_backup_rto_hours`).
Restore: deploy Forgejo, stop it, restore the database from `forgejo-db.sql` with `psql`, unpack
`repos/` into `forgejo_repo_dir` and `data/` into `forgejo_data_dir/data`, then start Forgejo and run
`forgejo admin regenerate hooks`.

## Monitoring (LOG-05)

`/metrics` on the HTTPS port needs `Authorization: Bearer <forgejo_metrics_token>`. Health:
`/api/healthz`. Access and router logs go to stdout (journald). Forgejo has no separate audit log;
admin and repository events are in the database (admin panel "System notices", repository activity).
